# CLAUDE.md — project conventions

File teach future Claude (and human) contributors load-bearing conventions of codebase. Keep short, honest.

## Stack

- Python ≥ 3.10 (target 3.10/3.11/3.12 in CI; embedded runtime 3.12.10).
- ComfyUI V3 API (`comfy_api.latest`) — no V1 `NODE_CLASS_MAPPINGS`.
- Vue 3 + Vite 5 + pnpm. Strict TypeScript.
- Vitest for frontend, pytest for Python.

## Directory contract

- `engine/` — pure Python, **zero ComfyUI imports**. Testable with vanilla pytest.
- `wp_nodes/` — ComfyUI V3 nodes. Named `wp_nodes` (not `nodes`) because ComfyUI repo-level `nodes.py` shadow any top-level `nodes/` package on `sys.path`.
- `src/` — Vue/TS frontend. Two Vite targets: `extension` (critical path, budget-gated) + `manager` (post-MVP SPA).
- `tests/` — Python tests. Use `conftest.py` sys.path shim.
- `scripts/` — Node helpers (bundle-size gate, size-delta diff, release helpers).
- `docs/widget-context-contract.md` — single canonical engine ↔ widget JSON shape doc. Update both Python (`engine/modules.py`) + TS (`src/widgets/_shared.ts`) sides in one PR when shape change.
- `docs/superpowers/{specs,plans}/` — gitignored per-contributor design docs + impl plans.

## Commands

```bash
pnpm build:extension   # produces js/main.js
pnpm build:manager     # produces web_dist/
pnpm test              # Vitest
```

## Load-bearing conventions

- **Engine isolation** — never import from `wp_nodes/`, `comfy_api`, or `torch` in `engine/`. Engine dict-free of ComfyUI globals. Break this break tests.
- **Internal keys** — context keys starting with `__` engine-internal; strip at socket boundaries (see `wp_nodes/types.py:strip_internals`).
- **Module IDs** — 8-hex-char short UUIDs. Match wildcard `@{uuid}` reference syntax planned for next spec.
- **V3 node IDs** — prefix `WP_`, category `wildcard-pipeline`.
- **Custom widget types** — `WP_CONTEXT_MODULES`, `WP_DEBUG_VIEWER`. Registered via `app.registerExtension({ getCustomWidgets })`. Assembler helper widget injected via `beforeRegisterNodeDef → onNodeCreated`, not `getCustomWidgets`, because sit alongside native STRING template widget.
- **Toast singleton** — one Vue app mounted to body-level div renders all toasts pushed via `src/components/shared/toast-store.ts`. Every Context node import same store so toasts surface from anywhere. Position mirror ComfyUI native PrimeVue toast anchor (rect-relative to `.graph-canvas-container`).
- **Subgraph traversal** — `collectUpstreamVariables` / `collectUpstreamValues` / `findDownstreamAssemblers` cross subgraph boundaries via `-10` SubgraphInputNode + `-20` SubgraphOutputNode sentinel ids. Walkers expect `app.graph` (root); per-call `buildSubgraphParents` map handle step-out. Use `walkAllNodes(rootGraph)` for graph-wide scans (e.g. pre-run validation).
- **Subgraph badges** — `extension/subgraph-badge.ts` attach `LGraphBadge` (via `window.LGraphBadge`) to any SubgraphNode containing WP nodes. Badge surface worst inner conflict severity with human label (e.g. `missing $foo`, `2 conflicts`). Wire via `nodeCreated` + `loadedGraphNode` hooks — `beforeRegisterNodeDef` does NOT fire for SubgraphNodes.
- **Conflict scanner** — advisory only; never block execution. Runtime last-write-wins. Rule types: `shadows_upstream` (info), `duplicate_variable` (warning), `missing_template_variable` (warning), `constraint_source_missing` / `constraint_target_missing` (warning — uuid not in catalog), `constraint_orphan_source` (warning — no source instance UPSTREAM), `constraint_orphan_target` (warning — the constraint's reach selector covers ZERO reachable downstream instances; per-selector, NOT count-aware — overlapping constraints may freely share an instance), `constraint_excludes_all` (warning — some source option leaves a covered target with no option of weight > 0 and no fallback; `extension/constraint-dead-ends.ts`, checks one constraint at a time and leans quiet when unsure). Engine emits runtime warnings `constraint_never_applied` (the reach matched nothing at runtime) and `constraint_partial_reach` (a `next N` / `pick` reach matched fewer instances than requested).
- **Constraint reach (SP3)** — each constraint carries a `target_select` reach selector: `{mode: "first"|"next"|"all"|"pick", count?, picks?}`, default `all`. Every constraint whose reach covers a firing downstream target instance applies, COMBINED — per-pick × per-tag × per-constraint multiply, with `exclude` (factor 0) absorbing. Mode `only` (linked picks, schema v6) turns its row into an allow-list: when the source fires, a target with no rule of its own in that row is excluded (by value on an exception, by tag in a matrix row; a matrix `allow` cell is NOT a mention because editors show it as Neutral; a target `accepts` axis the row rules on NO member of stays neutral, so a target that is also the source of another agreement is not shut out). No more one-shot/consumed-set: the engine counts per-constraint downstream hits in `ctx["__wp_constraint_hits__"]`. Reach is downstream-relative (counts from the constraint's own chain position) and cross-node + transitive (resolves `@{uuid}` at any depth). `pick` selects specific instances by `_uid` (direct top-level) or carrier `_uid` + option id (nested). The re-weight math is the pure `engine/modules/_constraint_math.py::combine_constraint_factor`, mirrored in TS at `src/manager/utils/constraint-math.ts` via the shared `tests/fixtures/constraint-corpus.json`. Published payloads using a non-default `target_select` stamp `schema_version = 4` (additive; community catalog v4).
- **Send-to-negative (schema v8)** — wildcard options, fixed values and combines carry an optional `negative` (same grammar as their value); derivation mode `negative` adds to a variable's negatives without writing it, and `negative_replace` swaps them for its value (test both with `isNegativeMode`). The engine files them per variable in `ctx["__wp_negatives__"]` (`engine/negatives.py`, cross-node key). Negatives FOLLOW USAGE: the Assembler's `negative` output only takes negatives of variables its template rendered; a write replaces a variable's negatives, append/prepend keep them. Negative text resolves on its own `key::neg` seed stream and refs inside it resolve quietly (no pick, no ref log, no hits, no chaining), so negatives never shift picks. A Context node or bundle child can override them per use: a `values_overrides` row's own `negative` key replaces the library row's (`""` clears it, no key keeps it), and a combine's `instance.negative_override`; wildcard option negatives stay library-only. Store an empty negative as absent. `$name.neg` / `$name.K.neg` reads a variable's negatives (`neg` rides the axis slot of the accessor grammar and is reserved: no `accepts` group may use it); it is not a read of `$name`, so it carries no negatives along. Both need v8.
- **Multi-action derivation clauses (schema v8)** — a branch or `else` runs its `action`, then each `extra_actions` entry in order (absent, never `[]`, for one action). Each action sees the previous one's write. Walk actions with `clause_actions` (Python) / `clauseActions` (TS); never read `.action` alone. Instance overrides key extra actions `"{bi}.{K}"` / `"else.{K}"` (`action_override_key` ≡ `actionOverrideKey`).
- **Wildcard fallback (schema v9)** — at most one non-null option per wildcard may carry `fallback: true` (stored only as `true`). It rolls like any option (weight, filters, toggles, constraints all apply; flagging never changes a normal draw) and is ALSO taken, without an rng draw, when nothing is live after weights + constraints (`engine/modules/_fallback.py:find_fallback`, run after filters + toggles) — top-level handler AND nested `ref_option_pool`. It replaces the `constraint_excludes_all_options` warning with an info `fallback_used`. Editors and probability helpers give it its normal share.
- **Model-aware pipelines** — `WP_ModelInfo` (`wp_nodes/model_info_node.py`) writes `$model_family` (from `model.model.model_config`'s class), `$model_variant` (file-name rules) and `$model_name`; the file name comes from following its `model` link through the hidden `prompt` (`engine/model_info.py::find_checkpoint_name`). Rules + stems mirror in TS at `src/extension/model-info.ts` via `tests/fixtures/model-variant-corpus.json`. Graph walkers treat it as a var source like the injector (kind `model`). Wildcard instance `match_variable` picks the option whose text equals that variable (else fallback, else roll + `match_variable_no_match`), which is how a variable becomes a constraint source. Workflow/instance state only, no schema bump.
- **Image Filter** — `WP_ImageFilter` (`wp_nodes/image_filter_node.py`, pure logic in `engine/image_filter.py`) is `is_input_list` with a FIXED slot set (no dynamic "any" outputs; `extra_1/2` are `MatchType`). A paused run waits in an `async execute` on the thread-safe `PENDING` store; the picker answers via `POST /wp/api/image-filter/answer` (`wp_api/image_filter.py`) after the `wp-image-filter` websocket event. "Stop" returns one `ExecutionBlocker(None)` PER output (a bare blocker does not block). Values batched like the frame's images are sliced (tensor dim 0, LATENT dict, CONDITIONING incl. `pooled_output`); everything else is kept/dropped with its frame. Picker answers may carry `edits` keyed `"f:i"` (`positive`/`negative` text, `mask` = PNG data URL whose ALPHA is the mask): with `same_shape` the first edited image of an item decides its prompt; an edited prompt is re-encoded only when the optional `clip` input is wired; once any mask is painted every output item gets a mask (incoming or empty). Send to Loop writes back through `editLoopConfig` (`widgets/context_loop.ts`).
- **AI chat context** — `engine/ai/docs_index.json` is the docs pages (plus Settings entries) as plain text for the chat; run `pnpm docs:index` after editing any docs page or `settings-index.ts` (the `docs-index` Vitest fails when it is stale). Editors call `registerOpenEditor` (`composables/useOpenEditor.ts`) so chat changes to the open item go into the draft, and views can `registerPageNote` to tell the chat what they show; a new editor or major view should do the same. Chat tools are declared once in `engine/ai/tools/catalog.py` (`Tool`: JSON-mode prompt line, native schema, groups); every call goes through `registry.check_args`, so a new tool is a catalog entry plus its runner. The server keeps each chat's turn log (`engine/ai/chatlog.py`, `ai_chats` tables, migration 020) and replays it on every request, so the browser sends only `{message, chat_id, page, events}`. Keep requests append-only for prompt caching: the library snapshot is frozen per chat (changes go in the message tail), JSON is `chatlog.dumps` (sorted keys), masking only moves forward, Ollama `num_ctx` stays fixed; `wp_api/_ai_chat.py` renders the log per provider (native tools or JSON steps) and sets Claude `cache_control` / OpenAI `prompt_cache_key`. Library search goes through `engine/ai/index.py`: an FTS5 cache DB next to the library (`*.ai-index.db`, synced lazily by `updated_at`; bump `FORMAT` to force a rebuild; falls back to the in-memory scorer without FTS5). `retrieve` puts gated top hits (and `docs.retrieve` pointers) in the message TAIL, never the system prompt. Opt-in meaning search (`embed_model`) fills item vectors in the background (`wp_api/_ai_embed.py`) and fuses them with keywords by RRF; Claude has no embeddings. Security (`/pr-drafts/ai-security.md`): keys are bound to the origin they were saved for (`config._key_for`; never send `cfg["api_key"]` anywhere else, embeddings use `embed_api_key`), the client never follows redirects, every `/wp/api/ai/*` route goes through `_ai_guard.guarded` (register new routes with `add(...)` in `wp_api/ai.py`; handlers live by feature in `wp_api/_ai_{drafts,turn,context,chats,pack,common}.py`), and everything the model reads or writes passes `engine/ai/safety.py` (`strip_invisible` / `clean`; untrusted text is labelled as data). Page tools (kind `client`: `open`, `read_page`, `highlight`, `select_rows`, and the delegates `draft_options` / `organize` / `show_test`) and `web_search` (kind `web`) PAUSE the turn: the server checks the args (`engine/ai/client_tools.py::prepare`), stores `meta.pending` and returns `pending`; the browser runs them (`composables/useAiActions.ts`; pages offer delegates with `registerAiAction`, pointable parts carry `data-ai-anchor` + `data-ai-label`) and resumes with `{chat_id, results}`. Every paused call gets a result (denied / "not run" on a new message), so the log stays append-only. Web tools (kind `web`) run server-side only after the user's Allow, or always with config `web_always_allow` (the user's choice, warned in Settings): `web_search` (`wp_api/_ai_search.py`, snippets, key bound to the engine host), `read_result` (`wp_api/_ai_web.py`: only a link the chat's own allowed searches returned, `meta.web_urls`; built-in reader is public-addresses-only via `_PublicResolver`, or the user's Crawl4AI / Firecrawl, config `reader`) and `danbooru` (config `danbooru_lookup`, read-only tag/wiki/related JSON, ≥ 1 s apart, never posts). Their text is formatted in `engine/ai/web_read.py` and labelled untrusted. Never give the chat any other tool that opens URLs, touches files or settings, or writes without a card. `lookup` (group `vocab`) searches the user's tag list / LoRAs / embeddings only while the browser says that autocomplete is on (`vocab` in the request, `engine/ai/vocab.py` + `wp_api/_ai_vocab.py`); the manager asks open canvas tabs for run-time variables over the `wp-canvas-facts` BroadcastChannel (`utils/ai-context.ts`, `extension/canvas-facts.ts`) and sends them as `canvas`. Replies render through `utils/chat-markdown.ts` (a parsed tree drawn with plain elements by `AiMessage.vue`: never `v-html`, links stay text). `check_args` checks list items and nested objects too and refuses a bad item rather than dropping it. Native-mode text that spells out a call ("I call: read {…}") is salvaged by `_ai_chat.salvage_calls`. The drawer width is `--wp-ai-chat-w` on the root (`composables/useAiChatWidth.ts`), shared with `AppLayout`'s page margin. Each turn also stores a `shown` entry (what the user saw; the model never reads it) so `GET /wp/api/ai/chats/{id}` can reopen a chat (`chatlog.display`); card actions are PATCHed as `meta.shown_status`. Pins are migration 021 (pinned chats are never pruned); rename and pin don't bump `updated_at`. `retry` truncates the log back to the last user entry and is refused (409) once a card from that turn was applied. `context` on each answer is the meter (`_context`); past `compact.TRIGGER` of the window, `engine/ai/compact.py` summarises everything before the last `KEEP_TURNS` turns into `meta.summary` (rendered at the head, so the prefix stays stable after). `stream: true` returns NDJSON events (`step`/`status`/`thinking`/`text`/`tool`, then `done` or `error`); providers are streamed and reassembled into their non-stream JSON (`_ai_chat._post`), and a server that refuses streaming is asked again without it (remembered in `_NO_STREAM`). Images (`/pr-drafts/ai-images-phase7.md`): the browser shrinks and re-encodes them (`utils/chat-image.ts`), the server checks and re-encodes them with Pillow (`wp_api/_ai_images.py`: data URL, strict base64, magic bytes, ≤ 1568 px / 1.15 MP, JPEG) and stores them on the user entry (`images`); providers get `image_url` parts / Ollama `images` / Claude image blocks; only the newest `chatlog.MAX_IMAGES_SENT` are sent (`images_before`, forward-only). `GET /wp/api/ai/vision` (`_ai_chat.vision_support`) decides whether the drawer allows attaching. Permissions (`/pr-drafts/ai-permissions-phase8.md`): config `allow_delete` / `auto_apply` (off by default; no tool reads or writes them). `delete_items` is offered only while `allow_delete` is on (`tools.sync_delete` re-syncs the chat's tool list each request and `_sync_permissions` tells the model once in the tail) and `Library.delete_items` refuses otherwise; `edit_categories` / `edit_tags` and deletes live in `engine/ai/chat_manage.py`, applied and undone by `composables/aiManageOps.ts` (a failed step rolls back what ran; Undo recreates items at their ids via the optional `id` on module/bundle/template create, which also clears bundle orphan flags). The server marks a proposal `risk: "low"` (update_info without a rating change, category creates); only those auto-apply.
- **Pack builder** — `engine/ai/pack/` (a package, one module per phase; `__init__` re-exports every name); the manager (`composables/usePackBuilder.ts`) holds all state and sends the plan + built items with every request. Plan v2: `settings` (`SETTINGS`), `decisions` (answered questions, never re-asked: `refine_text` lists them), `previous` (replays hand edits as the model's last answer), sections (a sub-bundle each), `MAX_ITEMS` = 60. `compile_plan` gives every item a key and a RESERVED 8-hex id, kept across refines and edits (match by kind + variable or name), so refs and constraints can point at unbuilt items. Extending a bundle passes `bundle_id`: `bundle_base` lists its children as `existing` items (keys `e…`, never edited or rebuilt), its vars count as set; `_extend_layout` is shared by `check_pack` and `extend_ops` so the tested order is the installed order; install is one `commit_import` with `replaces` (one undo restores the bundle). `engine/ai/bundle_split.py` only LABELS children; groups are runs of neighbours, so run order never changes. `DECIDE_ANSWER` mirrors in TS. Settings hold only preferences that apply to any pack (library, negatives, structure, style, rating, count, `model`); what a pack is about stays on the PLAN, read from the request or asked: `run` (`parse_run`: single / story with `frames` / sweep, kept across refines, editable by hand) and `inputs` (a given subject, LoRAs of any kind named `<slot>_lora`). `_settings_findings` checks what the run, LoRA inputs and `model` need (patches add the missing derivation; a LoRA standing in for a rolled pick gets a swap rule via `_lora_slot`), and a story's check plays each frame (`frame_pins`, `_merge_reports`). Draft with AI panels: `images` (checked by `_request_images`) and, when web search is set up, an optional `research` list (`engine/ai/research.py`, wildcard + text panels only) that the panel runs only after the user allows it (`useAiConversation.allowResearch`, `searched` sent with every later request).
- **Derivation NOT (schema v10)** — the condition editor's NOT toggle (`DerivationConditionTest.vue`: `partsOf` / `composeOp`) maps onto ops: equals↔not_equals, contains↔`not_contains`, matches↔`not_matches`, exists↔not_exists (NOT + has value → `is_unset`). Only `not_contains` / `not_matches` are new (stamp 10); a broken regex is false for both matches and not_matches.
- **AI page actions + checks** — `use_panel` (kind client) opens an item's editor and asks one of its AI panels (`client_tools.PANELS`; editors register it via `composables/usePanelAction.ts`, panels `defineExpose({ run })` through `useAiConversation.chat`); `show_test` also takes `from` / `pins` / `output` / `save` / `run`. `engine/ai/lint.py` checks every create/update proposal (scope bleed, duplicates, extreme weights, lookup-table derivations, constraints excluding without a fallback) into its warnings, and `proposal_note` feeds warnings back to the model. Warnings a card can settle itself carry `fixes` (`lint.fixes`, keys `scope:<concept>` / `dupes` / `weights`); the browser PATCHes `{pid, fix}`, the server records it in `meta["fixes"]` and returns the fixed body, and display + `_adopt_earlier` replay it through `lint.with_fixes`. Claude requests go through `_ai_client.claude_send`: newest models get no `temperature` and `tool_choice: auto` plus a written ask (a text JSON answer is parsed), unknown models are fitted after their first 400 and remembered. OpenAI itself (`_ai_chat.uses_responses`) goes through the Responses API, stateless (`store: false`, whole log every time): `responses_input` replays a step's `raw` items (encrypted reasoning, message with `phase`, kept calls; `chatlog.step_entry(raw=…)`) to the model that wrote them and rebuilds others; function tools are sent `strict: false`; no temperature or output cap (`/pr-drafts/ai-openai-responses.md`). A NEW unsaved item registers its editor under a reserved 8-hex id (`useOpenEditor.registerOpenEditor`, `editorForPage`; server `chat._add_unsaved`), so the chat reads and fills it and Save creates it at that id. `run_test` leaves `lib.last_card` (`chat_tools._test_card`), which the route puts on the step as `card` for `AiTestCard.vue`. Per-use clauses (`engine/ai/use.py`) take the module payload so options/rules are named by number. `ask` (kind `ask`, `engine/ai/ask.py`) pauses the turn on 1-4 questions shown inline (`AiAsk.vue`) WITHOUT holding the chat: the browser answers with numbers only (`{q, picked}` / `{q, other}` / `{q, decide}` via `useAiChat.answerAsk`), a new message answers it "in their own words"; answers land in `meta["decisions"]` (re-asking a header is refused, compaction appends them verbatim) and `meta["asked"]` (shown as `view.answered`); at most `MAX_ASKS` pauses per user message, never in a step with change or page tools. `retry: true` with a non-empty `message` is Edit last message.
- **Community tab iframe** — `views/Community.vue` frames `${WPC_API_URL}/embed-frame.html` (sandbox: scripts, same-origin, popups, forms, downloads; never top-navigation). The embed never runs in the ComfyUI origin and there is no `window.__wpcRuntime`: `community/frameBridge.ts` serves the frame's requests over postMessage (only `event.source === iframe.contentWindow` from the community origin) using `community/hostRuntime.ts` (`install` → `installEnvelope`, `markPublished`), checks every field (`cleanTarget`, `cleanDecisions`), and sends route changes, theme and the publish hash as events (the hash is stripped from the address bar once forwarded). Protocol in `community/frame-protocol.ts`, mirrored in the community repo's `web/src/frame/protocol.ts` (additive only; bump `FRAME_PROTOCOL` in both on a rename). Tokens live on the community origin; old `wpc.embed.*` keys go over once in `hello` and are wiped on `tokens-adopted`. No `ready` within 10 s shows the offline card.
- **Bundle-size gate** — entry `main.js` must stay ≤ 30 KB gzipped (hard). Total `js/` budget 496 KB is a guide: over it `pnpm size` warns, 5% past it fails. Pre-commit run `pnpm build:extension && pnpm size`. Raise `TOTAL_LIMIT` with a dated note saying why.
- **Coverage gate** — vitest v8 coverage with thresholds (lines/statements 80%, functions 66%, branches 77%, `vitest.config.ts`) and pytest `fail_under = 88` (`pyproject.toml`; CI runs pytest with `--cov` so it applies). Both sit a few points under the measured baseline; ratchet up alongside new tests, never down. CI also runs `pnpm check:css-isolation`.
- **Caching** — `WP_Context` + `WP_Debug` set `not_idempotent=True` so seed cycling always re-executes.
- **Conventional Commits** — enforced by commitlint. semantic-release read log to cut versions. `main` cuts releases; pushing to `beta` cuts prereleases (`x.y.z-beta.N`), which keep `docs/release-notes/next.md` for the final release and skip the Comfy Registry publish.
- **Extension isolation — four layers**:
  1. **CSS class namespace**: every class selector starts with `.wp-*` (or `.var-1..8`). Never write a top-level rule with an unprefixed class — it could collide with ComfyUI core or another custom node. New top-level non-`wp-*` selectors are blocked by `pnpm check:css-isolation`.
  2. **`@layer wp-extension` wrap**: standalone extension CSS (`a11y.css`, `display-prefs.css`, `ContextWidget.vue` unscoped block, etc.) sits in `@layer wp-extension { ... }` so host CSS (unlayered) beats us on any selector collision. Layered author rules are subservient to unlayered ones in the same origin. NOT applicable to CSS that gets `@imported` into Vue `<style scoped>` blocks — the scoper can't parse `@layer` atrules; rely on namespace prefix there.
  3. **WeakMap stashes for litegraph object metadata**: never attach state to nodes/slots via string keys (`node._wpFoo = ...`). Use the WeakMaps in `src/extension/_stashes.ts` — module-private, no collision risk with other extensions, invisible to workflow serialization. Method overrides (`getInputPos`, `onConnectionsChange`, etc.) must keep their standard names because litegraph reads them; isolation there is via wrap-and-call-original chaining.
  4. **Persistent state on `node.properties` only**: anything that must survive workflow save lives on `node.properties[key]` with a `wp_*` / `collapse_connections`-style string key (workflow JSON is the serialization root). Transient session state belongs in WeakMaps.

## Frontend overview

- **Entry** `src/main.ts` → `js/main.js` (~4 KB gzip). One top-level `await import("./boot")` preload widget glue so `getCustomWidgets` factories run sync (Promise return → `{widget: undefined}` and widget never mount; ComfyUI does not await an async `getCustomWidgets`).
- **Boot chunk** `src/boot.ts` — everything registration + node creation need, re-exported from ONE module so it ship as ONE chunk (empty canvas = `main.js` + `boot-*.mjs`). Before, each preload was own `import()` and shared deps split out: 43 files. Only add what registration needs; anything reached by user action (modal, toast stack, subgraph badge) gets a `load*` helper in `boot.ts`, not an `import()` in `main.ts` (a chunk loaded from `main.ts` makes Rollup split vue + stores back out).
- **Widget glue** `src/widgets/*.ts` — one mount glue per widget, in the boot chunk. Each loads its SFC via `defineAsyncComponent` (`ContextWidget`, `DebugViewer`, `AssemblerHelper`, `RichTextInput`, …) so SFC chunks download only when a matching node exists.
- **Shared** `src/widgets/_shared.ts` expose `createDomWidgetHost`, JSON helpers (`parseWidgetJson`, `parseWidgetJsonWithRecovery` for corrupt-workflow recovery path), shared types. Lives in boot chunk with Vue runtime.
- **Graph + conflicts** `src/extension/{graph,conflicts,subgraph-badge,reactive,graph-events}.ts` — pure logic, no DOM. Imported by widgets, easy to unit-test isolated.
- **Reactivity** `extension/reactive.ts:reactiveFromGraph` — wires `onConnectionsChange` chain + 400ms polling fallback + `afterConfigureGraph` re-sync so widgets recompute on graph edits + workflow loads without flashing stale state.
- **Adding new widget**: (1) write SFC under `src/components/<name>/`, (2) add `src/widgets/<name>.ts` exposing `create(node, inputName)` that return `createDomWidgetHost(...)`, (3) re-export it from `src/boot.ts` and wire in `src/main.ts` — either as `getCustomWidgets` entry (for inputs declared with matching widget-type) or via `beforeRegisterNodeDef → onNodeCreated` (for free-floating helpers). SFC via `defineAsyncComponent`, never static import, so boot chunk stay small.

## Schema versioning + lazy migration machine

Spec: `D:\Desktop\Wildcard-Pipeline-Community\docs\superpowers\specs\2026-06-05-schema-versioning-migration-design.md` (cross-repo lock; read before bumping).

**Three axes** every payload + library row carries:

1. **`schema_version`** (per row, engine column added in migration 014): which payload shape this row's `payload` is in. Single version per payload root — bundles' children inherit the bundle's `schema_version`.
2. **`producer_engine_version`** (per published community version, server-side only): diagnostic. Never load-bearing.
3. **`version_number`** (per community post, server-side): the user-facing 1/2/3 publish revision. Unrelated to schema_version.

**Engine row columns** (migration 014):
- `schema_version INTEGER NOT NULL DEFAULT 1` — current shape this row targets.
- `original_payload_json TEXT` — verbatim local mirror of the payload as it arrived from community (or import). Lazy migrator reads from here, never from the live `payload` field. Lets us re-project from the original if a migrator chain gets fixed retroactively.
- `tolerant_drift_status TEXT` — `none` | `tolerant` | `strict`. Set by parseTolerantAsCurrentShape during install.
- `schema_migrated_at TEXT` — wall-clock stamp of last lazy migration step.

**Which number goes where** (three constants, one job each — don't collapse them):

- **`CURRENT_SCHEMA_VERSION` = 2** (`src/manager/import-export/migrations.ts`, mirrored in `engine/migrations/__init__.py`): head of the migration chain. Stays 2 because v3–v10 are additive and need no migrator.
- **`MAX_KNOWN_SCHEMA_VERSION` = 10** (same two files): the highest version this runtime reads + writes natively. Sent to the framed community embed as `hello.schemaVersion` (`src/manager/community/hostRuntime.ts`) and the ceiling above which `migrateImportEnvelope` refuses a pack.
- **Content stamp** (`schemaVersionForPayload` in `src/manager/import-export/single-row-publish.ts`): what publish sends — the LOWEST version the payload's features need (2 baseline, 3 SP2b range/`~` grammar, 4 non-default constraint `target_select`, 5 a wildcard `accepts` tag axis, 6 a constraint `only` rule, 7 a derivation branch with AND/OR groups or `is_empty`/`is_not_empty`, 8 a non-empty `negative`, a derivation "Add to negative" / "Replace negative" action, `extra_actions` or a `$name.neg` read, 9 a wildcard option flagged `fallback`, 10 a derivation test `not_contains` / `not_matches`).

A pack arriving from the community keeps the stamp the server stored for it (`CommunityDownload.schema_version`, fed to `wrapAsEngineExport` / the dependency downloader) so install migrates it from where it actually is. Never stamp a received pack with a constant. Local round-trips of live rows (e.g. `BundleEditor` extract) stamp `MAX_KNOWN_SCHEMA_VERSION`.

**The machine** — what actually runs today (checked 2026-10-16): install goes `parseCheckedPayload` (`shape-check.ts`: `parsePayload` → `migrateImportEnvelope`, which refuses a pack above `MAX_KNOWN` and passes `CURRENT < v ≤ MAX_KNOWN` through untouched → each module row's `payload` against the strict validator's payload schema at CURRENT, and bundle children's id/type; nothing is stripped) → `POST /import/commit`, which runs each module's and bundle child's engine `validate_payload` and refuses the commit on the first failure (`wp_api/import_export.py:_validate_payload_shapes`). Both sides refuse the same packs, so a validator stricter than the engine is a bug (the engine's defaults, like a missing option weight, are optional in the validators). `shape-check.ts` loads Zod, so `install.ts` imports it dynamically; keep it out of the canvas ContextWidget chunk. The pieces below are BUILT AND TESTED BUT NOT WIRED into any production path: `decideInstallPath`, `parseTolerantAsCurrentShape`, `migratePayload` / `registerMigrator`, and `lazy_migrate_row` (only migration 014 calls it, with no migrators). Nothing sets `tolerant_drift_status` or `original_payload_json` from the SPA. Harmless while every row is at `CURRENT = 2`; the next SHAPE-CHANGING bump must wire them first (install branch + a read path through `lazy_migrate_row`) instead of assuming they run. The intended design:

- **Validator registry** (`src/validators/index.ts:getValidator`): one Zod validator per shape-changing `schema_version` (v1, v2). v3–v10 didn't change a shape, so they validate against v2. Tolerant mode (`.strip()`) is for installing newer payloads (`parseTolerantAsCurrentShape`).
- **`parseTolerantAsCurrentShape(raw, currentVersion)`** (`src/manager/import-export/tolerant-parse.ts`): strips fields the current shape doesn't know, returns the projection that matches `currentVersion`. Used at install when source `schema_version > CURRENT`.
- **`migratePayload(payload, from, to)`** (`src/manager/import-export/migrations.ts`, beside the envelope-level `migrateImportEnvelope`): forward-only chain. Each step is a registered function in the migrators map. `from > to` is illegal — no downgrades.
- **`lazy_migrate_row(row, currentVersion, migrators, validators)`** (`engine/db/lazy_migrate.py`): reads `original_payload_json` (or `payload` if absent), walks the migrator chain to `currentVersion`, validates, writes back. Bulk-at-boot runner is eager iteration of this routine.
- **Install decision tree** (`src/manager/import-export/install.ts`): branches on `source_schema_version` vs `CURRENT_SCHEMA_VERSION`:
  - `=`: strict validate + insert.
  - `<`: migratePayload then strict validate + insert.
  - `>` and tolerant-only diff: parseTolerantAsCurrentShape, mark `tolerant_drift_status='tolerant'`, insert.
  - `>` and breaking-future diff (per catalog `is_breaking_from_previous` AND-fold across the interval): refuse install with a clear error.

**Server probe**: the host bridge sends `MAX_KNOWN_SCHEMA_VERSION` in its `hello` to the framed embed, which shows it to the embed views as `__wpcRuntime.schemaVersion` inside the frame; it ships in the sister bundle, not fetched from server. The community embed refuses to install a pack stamped above it. Server-first deploy ordering (see community CLAUDE.md) means the community catalog always reflects shapes ≥ sister's MAX_KNOWN.

### Bumping `schema_version` (the proper way)

When a payload shape change lands (not a row-column change — those don't bump schema):

**Additive bump** (an optional field, new enum value or new text grammar an old runtime can safely lack — v3 through v10 all were):

1. **Add the version constant** next to `TAG_AXES_SCHEMA_VERSION` / `CONSTRAINT_ONLY_SCHEMA_VERSION` in `migrations.ts` (and `engine/migrations/__init__.py`), with a comment saying what triggers it.
2. **Teach `schemaVersionForPayload`** AND its Python mirror `engine/migrations/stamping.py` to return it only when the payload actually uses the feature (structural walk, bundle children + instance overrides included), and add cases to `src/manager/__tests__/import-export/publish-stamping.test.ts` + `tests/engine/test_schema_stamping.py`.
3. **Bump `MAX_KNOWN_SCHEMA_VERSION`** in `migrations.ts` AND `engine/migrations/__init__.py`, and update the drift guard in `schema-version-fork.test.ts` to exercise the new highest stamp.
4. **Make sure the strict validator keeps the new field** (it strips unknown keys) — `src/validators/module/v2.ts` + the engine-parity test.
5. **Catalog row** — step 7 below. `CURRENT_SCHEMA_VERSION` does not move.
6. **AI assistant** — the model never writes payloads; `engine/ai/` compiles them (`wildcard`, `derivation`, `constraint`, `pack`, `chat`). A feature the assistant should author needs its compiler + schema + prompt there, with tests.

**Shape-changing bump** (needs a migrator):

1. **Add the new shape's validator.** New file under `src/validators/module/v<N>.ts` (and `bundle/` if needed). Register every subtype at `N` in `src/validators/index.ts`.
2. **Add the migrator step.** In `src/manager/import-export/migrations.ts`, add to `MIGRATION_CHAIN` (envelope) and/or `registerMigrator` (per row), and mirror it under `engine/migrations/`. Forward-only. The function is pure — no side effects.
3. **Add fixtures.** Under `src/validators/fixtures/v<N>/` — at minimum a strict-valid module per subtype, plus a migrated-from-v<N-1> round-trip case in `src/manager/__tests__/import-export/migration-machine.test.ts`.
4. **Bump the constants.** `CURRENT_SCHEMA_VERSION` and `MAX_KNOWN_SCHEMA_VERSION` to at least `N`, in both `migrations.ts` and `engine/migrations/__init__.py`.
5. **Write the migration test.** `tests/engine/db/test_lazy_migrate.py` should cover v<N-1>→v<N> round-trip + the breaking-future path if applicable.
6. **Run `pytest tests/engine/ -q && pnpm test` until green.** Sister pre-commit hook (~2 min) also runs lint + typecheck + build + size; expect that wait.
7. **Coordinate the community-side catalog row.** Community web's `schema_catalog` table gets the matching `(version, is_breaking_from_previous, notes)` row + a deploy that lands BEFORE sister's PR merges. See community CLAUDE.md "Bumping the schema" for the server side.
8. **Sister deploys after server.** Once catalog HEAD ≥ sister's MAX_KNOWN, sister can safely publish the new stamp and refuse breaking-future shapes.

### Validator ↔ engine parity (DON'T skip)

The community TS validators in `src/validators/` are a hand-authored
re-implementation of the engine's payload shapes, and re-implementations
drift — fixed_values shipped for weeks as `entries/{variable_name}` when
the engine has always used `values/{id,name,value}`. The guard against
this:

- `scripts/dump_engine_shapes.py` builds one sample payload per subtype,
  validates each against that subtype's **own engine `Handler.validate_payload`**
  (the authority — raises if not engine-valid), and writes the engine-row
  shape to `src/validators/fixtures/engine-parity/*.json`.
- `src/validators/__tests__/engine-parity.test.ts` asserts the **strict**
  community validator accepts every one of those fixtures.
- `tests/test_engine_parity_fixtures.py` re-runs the dump in memory and fails
  pytest when a committed fixture is stale, so forgetting the script is
  caught in CI.

**Any time you change an engine module payload shape** (a `*_handler.py`
`validate_payload`, or what the editor stores), run
`python scripts/dump_engine_shapes.py` and commit the regenerated
fixtures. If the sample no longer validates against the handler, the
script fails — update the sample. If the TS validator then rejects the
new shape, the parity test fails — update the validator. Either failure
means the two have diverged; fix it before publish breaks for a user.

### Row-level column changes (no schema_version bump needed)

The most recent example is **migration 015 (`content_rating` column)**. Adding a column to `modules` or `bundles` is just an Alembic-style SQLite migration — no payload-shape change, no validator update, no migrator chain. Procedure:

1. **New file** `engine/db/migrations_sql/<NNN>_<name>.py` mirroring 013/015 shape: `_has_column` gate + `with conn: conn.execute("ALTER TABLE … ADD COLUMN …")` for both `modules` and `bundles` if the field applies to both.
2. **Update `_row_to_module` / `_row_to_bundle`** in `engine/db/repositories.py` — wrap the new column read in `try/except (IndexError, KeyError)` so pre-migration fixtures don't blow up.
3. **Update `ModuleRepository.create/update` + `BundleRepository.create/update`** to accept the new field as a kwarg.
4. **Update `_insert_module` / `_insert_bundle` (+ `_update_module` / `_update_bundle` if needed)** in `engine/importer.py` to pass the field through from the entity dict. Use `COALESCE(?, col)` on the UPDATE side when you want missing-in-content to preserve existing value (NOT overwrite to NULL).
5. **Update `wp_api/modules.py` + `wp_api/bundles.py`**: add the field to `_UPDATABLE_FIELDS` + plumb into the create handlers.
6. **TS types**: extend `ModuleRow` / `BundleRow` + `*CreateInput` / `*UpdateInput` in `src/manager/api/types.ts`.
7. **Bump the head-migration test**: `tests/engine/db/test_migrations.py:test_migrate_records_version` asserts the head version — update to `<NNN>`. Same for the expected-columns set tests.
8. **Write a migration test** at `tests/engine/db/test_migration_<NNN>.py` — column exists, default backfill correct, idempotent rerun, accepts the new values.

If the column also flows through the host-bridge install seam (community origin metadata), extend `InstallOrigin` in `src/manager/import-export/install.ts` AND the embed's `HostInstallOpts.origin` in `web/src/embed/EmbedDetail.vue` (community web repo). Map community-side naming → engine-side naming at the seam if they differ (e.g. `'sfw'` → `'safe'`).

## Anti-patterns (inherited from reference project `ComfyUI-Wildcard-Pipeline`)

- Never use V1 `NODE_CLASS_MAPPINGS` / `EXTENSION_WEB_DIRS`.
- Never `console.log` for user warnings — use ComfyUI toast API.
- Never use `getInputNode()` / `findInputSlot()` — walk via `node.inputs[].link → app.graph.links[linkId] → graph.getNodeById(link.origin_id)`.
- Never use `requestAnimationFrame` in `onConnectionsChange`; link already established when callback fires.
- Never register SPA catch-all route before API routes.
- Never suppress types with `as any`, `@ts-ignore`, `@ts-expect-error`.
- `cssInjectedByJsPlugin` required, not optional. Vite library mode emit CSS files but never inject `<link>` tags, and ComfyUI load our `main.js` as bare ES module so `<link rel="modulepreload">`-style auto-loading does not apply. Per-chunk runtime injection (`relativeCSSInjection: true`) keep entry chunk CSS-free — styles only get injected when owning lazy chunk loads. This what every Vue-based ComfyUI extension in wild does (see `ComfyUI-Easy-Use/web_version/v2/easyuse.js`).
